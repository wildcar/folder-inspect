## A. Уточнение задачи

Исходная формулировка: «проверка хранилища файлов на наличие очень больших файлов,
архивов, мусорных файлов, дублирующихся файлов; цель — почистить репозитории от ненужных файлов».

### A1. Что именно сканируем
Что такое «хранилище» и «репозитории» в вашем случае?
- (a) обычные папки на локальном диске (проекты, документы, загрузки)
- (b) именно git-репозитории — рабочие копии
- (c) git-репозитории, включая историю (`.git/objects`) — поиск больших файлов, уже закоммиченных
- (d) сетевые шары / NAS / внешние диски
- (e) несколько корней за один запуск

**По умолчанию:** (a) + (b) — любая папка, с распознаванием git-репозиториев внутри неё; история git — позже.

### A2. Объёмы
Типичный размер сканируемого дерева?
- до 10 тыс. файлов / до 10 ГБ
- до 1 млн файлов / до 1 ТБ
- больше

**По умолчанию:** до 1 млн файлов / 1 ТБ. Влияет на хеширование дубликатов, параллелизм и кеш между запусками.

### A3. Целевые ОС
- только Windows
- Windows + Linux
- Windows + Linux + macOS

**По умолчанию:** Windows + Linux.

### A4. Кто пользователь
- только вы
- небольшая техническая команда
- нетехнические пользователи (нужен «дружелюбный» интерфейс и подсказки)

**По умолчанию:** вы + техническая команда.

### A5. Режим использования
- разовые проверки вручную
- регулярно по расписанию (планировщик / cron), с историей и сравнением сканов
- в CI / pre-commit хук: непройденная проверка = ненулевой код выхода

**По умолчанию:** вручную + пригодность для CI (exit code, машиночитаемый отчёт).

### A6. «Очень большие файлы»
- порог по умолчанию (например, > 50 МБ)? Настраиваемый через конфиг/флаг?
- отдельный, более строгий порог для файлов внутри git-репозиториев (например, > 5 МБ)?
- показывать топ-N самых больших файлов и папок независимо от порога?

**По умолчанию:** порог 50 МБ (в git — 5 МБ), настраивается; топ-20 файлов и папок в отчёте.

### A7. Архивы
- определять только по расширению (`.zip .7z .rar .tar.gz .iso ...`) или по сигнатуре (magic bytes)?
- заглядывать внутрь: перечислять содержимое, искать вложенные архивы, считать распакованный размер?
- считать ли архивом `.docx/.xlsx/.jar/.apk` (технически это zip)?

**По умолчанию:** расширение + сигнатура; внутрь не смотрим; офисные форматы и jar/apk архивами не считаем.

### A8. «Мусорные» файлы
Что относится к мусору? Отметьте нужное или дополните:
- зависимости и сборка: `node_modules/`, `dist/`, `build/`, `target/`, `bin/`, `obj/`, `__pycache__/`, `.venv/`
- кеши IDE/инструментов: `.idea/`, `.vs/`, `.vscode/` (спорно), `.gradle/`, `.pytest_cache/`
- временные: `*.tmp`, `*.bak`, `*.old`, `*.orig`, `~$*.docx`, `*.swp`, `*.log`
- системные: `Thumbs.db`, `.DS_Store`, `desktop.ini`
- пустые папки, файлы нулевого размера, битые симлинки
- файлы, не изменявшиеся дольше N лет

Нужен ли **настраиваемый список правил** в стиле `.gitignore`? Учитывать ли `.gitignore` самого репозитория
(файлы, попавшие под ignore, но лежащие в рабочей копии — кандидаты на удаление)?

**По умолчанию:** встроенный набор правил + пользовательский конфиг в синтаксисе gitignore; учёт `.gitignore` репозитория; пустые папки и нулевые файлы — да; по возрасту — выключено.

### A9. Дубликаты
- только точные (одинаковое содержимое, по хешу)?
- «похожие»: одно имя в разных папках, версии `report_v2_final(1).docx`?
- искать дубликаты между разными корнями сканирования?
- минимальный размер файла для проверки (мелочь игнорировать)?

**По умолчанию:** точные по содержимому (размер → частичный хеш → полный хеш), между всеми корнями, минимум 1 КБ. Похожие имена — отдельный «мягкий» отчёт без предложения удалить.

### A10. Действия над найденным
- только отчёт (read-only)
- удаление с подтверждением
- перемещение в корзину ОС
- перемещение в «карантинную» папку с возможностью откатить
- замена дубликатов на hardlink / symlink
- генерация предложений в `.gitignore`

Обязателен ли режим `--dry-run`? Нужен ли интерактивный выбор (чекбоксы) перед действием?

**По умолчанию:** read-only по умолчанию; действия — только по явному флагу, с dry-run и планом действий, который можно сохранить и применить. Первая версия: отчёт + карантин.

### A11. Формат отчёта
- консоль (таблицы, цвет)
- JSON (для CI и других инструментов)
- CSV / Excel
- HTML / Markdown (для отправки коллегам)
- история сканов и сравнение «что изменилось с прошлого раза»

**По умолчанию:** консоль + JSON; HTML и история — вторая очередь.

### A12. Исключения и безопасность
- как задавать исключения: пути, glob-маски, конфиг-файл в корне (`.folder-inspect.yml`)?
- следовать ли по симлинкам/junction за пределы корня?
- есть ли «защищённые» зоны, которые нельзя трогать никогда (`.git/`, системные папки)?

**По умолчанию:** конфиг в корне + флаги; по симлинкам не ходим; `.git/` и системные папки только читаем, никогда не изменяем.

## B. Платформа, язык, интерфейс

### B1. Интерфейс
- CLI (команды и флаги)
- TUI (интерактивный интерфейс в терминале: дерево, чекбоксы)
- Desktop GUI (окно)
- Web UI на localhost (открывается в браузере)
- комбинация: CLI-ядро + один из интерфейсов поверх

**По умолчанию:** CLI-ядро с машиночитаемым выводом, к которому позже можно добавить TUI или web UI.

### B2. Язык / рантайм
Есть ли предпочтения, ограничения или уже накопленный опыт в команде?

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Go** | один exe без зависимостей, быстрый обход ФС, кросс-компиляция, простой параллелизм | GUI слабый; TUI (bubbletea) хороший |
| **Rust** | максимальная скорость, надёжность | дольше разрабатывать |
| **Python** | быстро писать, богатая экосистема | нужен интерпретатор; раздача на Windows неудобна; медленный обход |
| **Node / TypeScript** | в репозитории уже разрешён npm; легко сделать web UI | нужен Node; тяжёлые node_modules; хеширование медленнее |
| **C# / .NET** | нативно для Windows; WPF/WinUI для GUI; single-file publish | кросс-платформенный GUI сложнее |
| **PowerShell** | ничего не устанавливать на Windows | плохо для больших объёмов; Linux — с оговорками |

**По умолчанию (рекомендация):** Go — утилита «один бинарник», под Windows и Linux, с хорошей скоростью обхода и хеширования.

### B3. Дистрибуция
- один исполняемый файл без установки
- установщик (msi / winget / choco / scoop)
- пакет (pip / npm / cargo install)
- контейнер
- скрипт в репозитории

**По умолчанию:** один исполняемый файл + GitHub Releases.

### B4. Зависимости
- разрешены сторонние библиотеки?
- или максимально стандартная библиотека?

**По умолчанию:** сторонние — можно, но минимально и только проверенные.

### B5. Производительность
- параллельный обход и хеширование?
- инкрементальное сканирование: кеш хешей между запусками (по пути + размеру + mtime)?

**По умолчанию:** параллелизм — да; кеш — вторая очередь.

### B6. Конфигурация
- только флаги командной строки
- конфиг-файл (yaml / toml / json) в корне сканируемой папки и/или в домашней папке
- оба, флаги переопределяют файл

**По умолчанию:** оба; формат — YAML.

### B7. Локализация
По `AGENTS.md`: текст для пользователя на русском с возможностью расширения.
- нужен ли английский сразу в первой версии?
- язык определять по ОС или флагом?

**По умолчанию:** русский + английский с первой версии, выбор флагом, автоопределение по ОС.

### B8. Тестирование
- ожидаемый уровень: unit-тесты ядра + интеграционные на сгенерированной тестовой папке?
- нужна ли фикстура-генератор «грязной» папки для тестов и демонстрации?

**По умолчанию:** да и да.

### B9. Лицензия и публичность
- MIT / Apache-2.0 / другая / без лицензии (private)

**По умолчанию:** MIT.
